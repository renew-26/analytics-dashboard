# 대시보드 로딩 개선 계획

측정일 2026-09-09. 측정 환경은 `npm run dev`(로컬), 워밍업 후 2회차 기준.
프로덕션 빌드는 렌더링이 더 빠르지만 **행을 받아오는 비용은 동일**하다.

## 증상

| 페이지 | 응답 |
|---|---:|
| `/` | 2.4s |
| `/companies` | 1.6s |
| `/categories` | 1.6s |
| `/categories/정수기` | 2.2s |
| **`/company/코웨이`** | **3.5 ~ 4.8s** |

## 원인

**Postgres가 할 group-by를 Node가 대신 하고 있다.** 집계에 필요한 건 수십 행인데
원장 전체를 네트워크로 옮겨와 JS에서 센다. 렌탈사 상세 한 장이 받는 양:

| 쿼리 | 행 | 시간 |
|---|---:|---:|
| 본문용 주문확정 2025-01~ | 18,566 | 1.46s |
| 포지션 경쟁군 8사 2026-01~ | 40,757 | 1.31s |
| IA·티어용 계약완료 12개월 | 20,207 | 1.64s |
| TypeA 판정 count ×3 | — | 0.32s |
| **합계** | **약 80,000행** | **4.4s** |

여기에 두 가지가 겹친다.

1. **쿼리 6~7개가 전부 순차 `await`** 다. 서로 의존하지 않는데도 시간이 그대로 더해진다.
2. **`app/` 아래 21개 페이지가 전부 `force-dynamic`이고 `revalidate`가 한 곳도 없다.**
   데이터는 하루 한 번(사기준 05:00 동기화) 들어오는데 요청마다 전량 다시 받는다.

## 1단계 — 코드만 (부작용 없음) ✅ 2026-09-09 적용

`app/company/[company]/page.tsx` 의 독립 조회를 함수 진입부에서 시작만 걸고 쓰는
자리에서 `await` 하도록 바꿨다 (`periodP` · `iaAllP` · `shareRowsP` · `typeInfoP` →
`growthRowsP` · `typeaPoolP`).

**측정 결과 — 데이터 계층은 확실히 빨라졌다:**

| | 같은 3개 조회(79,530행) |
|---|---:|
| 순차 | 4,043ms |
| 병렬 | **1,936ms** |

**그런데 페이지 전체 응답시간은 개선을 확인하지 못했다.** dev 서버에서 병렬/순차를
번갈아 바꿔가며 5회씩 중앙값을 재봤으나, **같은 코드를 두 번 잰 값의 차이(3.5s ↔ 4.7s)가
조건 간 차이보다 커서** 신호가 노이즈에 묻힌다.

부수적으로 확인한 것:

- **JS 집계는 병목이 아니다** — 80,000행 집계 루프가 20ms.
- dev 응답시간의 상당 부분은 dev 모드 컴파일·렌더 오버헤드다
  (서버 렌더 로그 기준 SK_I 0.5s · 헬로비전 0.9~1.4s · 교원웰스 1.8s).

**프로덕션 빌드 측정 (2026-09-10, 5회 중앙값):**

| 페이지 | 중앙값 | 범위 |
|---|---:|---|
| `/company/코웨이` | **2.49s** | 2.33 ~ 4.79 |
| `/companies` | 1.75s | 1.41 ~ 5.48 |
| `/` | 2.32s | 1.82 ~ 3.62 |

dev(3.5~4.7s)보다 빠르지만 **여전히 느리고 편차가 크다**(같은 페이지가 1.4s ~ 5.5s).
병렬/순차 A/B 는 빌드를 두 번 돌려야 해서 여기서 멈췄다 — 다음에 이어서 잴 것.

**아직 안 한 것 — Suspense 스트리밍.** KPI를 먼저 흘리고 무거운 섹션(포지션·경쟁
분석·점유율)을 뒤로 넘기면 총 시간은 같아도 **빈 화면을 보는 시간**이 사라진다.
2,400줄짜리 페이지에서 섹션 600줄+를 자식 컴포넌트로 들어내야 해서 손이 크다.

### 배운 것

병렬화는 **기다림을 겹치는 것**이지 **일을 줄이는 것**이 아니다. 8만 행을 받는 일
자체는 그대로 남는다. 체감을 바꾸는 건 2단계(같은 일을 다시 안 하기)와
3단계(받는 양 자체를 줄이기)다.

## 2단계 — 캐시 (스테일 트레이드오프 결정 필요)

`export const revalidate = <초>` 를 걸면 첫 방문자만 비용을 내고 나머지는 즉시다.
결정할 것은 **허용 스테일 시간** 하나다 — 5분 / 1시간 / 동기화 시각까지.

⚠️ 마이그레이션 진행 중에는 동기화 직후 숫자를 바로 확인해야 할 수 있다.
`docs/` 의 마이그레이션 상태와 함께 판단할 것.

## 3단계 — 근본 (DB 작업 필요)

가장 무거운 건 포지션 차트용 4만 행이다. 필요한 값은 "회사 × 카테고리 건수" 수십 개뿐.
TypeB 렌탈사는 렌탈사 필터조차 없어 전 렌탈사를 훑는다.

**(가) PostgREST 집계 함수 켜기 — 권장.**
현재 이 프로젝트는 꺼져 있다(확인: `select=...count()` 요청이 `PGRST123: Use of
aggregate functions is not allowed`). 켜면 `select=rental_company,category,count()` 로
**4만 행 → 40행**이 되고 페이지 코드의 집계 루프도 같이 사라진다.
프로젝트 전역 설정이라 승인 필요.

**(나) RPC 함수 / 머티리얼라이즈드 뷰.**
집계 SQL을 마이그레이션으로 넣고 `supabase.rpc()` 로 부른다. 더 정교하지만
`migrations/2026-09-04_phase2_views.sql`(PHASE 2 대기 중)과 겹치는지 먼저 확인해야 한다.

3단계까지 가면 렌탈사 상세는 0.5초권으로 내려간다.

## 손대지 않은 것

- 경계선 아래(사이드바 `기타 분석`) 레거시 페이지의 성능은 측정만 하고 두었다.
- `raw_orders` / `raw_contracts` 인덱스 상태는 확인하지 않았다. 3단계 전에 볼 것.

## PHASE 2 전 기준선 (캐시 전)

측정일 2026-09-11. base URL `http://localhost:4100`(프로덕션 빌드, `npm run build && PORT=4100 npm run start`).
`~/.claude/scripts/measure-pages.mjs`로 페이지별 1차 요청과 2차 이후 5회 중앙값을 잰 결과:

```
base=http://localhost:4100  runs=5

페이지                             1차      2차 중앙값  범위
/                           1984ms      1712ms  1540~2105ms
/companies                  1215ms      2265ms  1263~3111ms
/categories                 1962ms      2386ms  1396~3078ms
/categories/정수기             2106ms      3861ms  2460~4599ms
/company/코웨이                6701ms      5452ms  3306~8331ms
/exception-approval         8797ms       950ms  763~1045ms
```

6개 페이지 전부 HTTP 200. 캐시가 없는 상태이므로 조건이 성립한 페이지(`/`, `/companies`,
`/categories`, `/categories/정수기`, `/company/코웨이`)는 1차와 2차가 비슷하게 느리다.
`/exception-approval`만 1차(8797ms)가 2차 중앙값(950ms)보다 크게 높게 나왔는데, 재현
여부는 확인하지 않았다 — PHASE 2 캐시 도입 후 전후 비교 시 이 페이지는 참고만 할 것.

이 표가 **PHASE 2(캐시) 적용 전의 기준선**이다. 같은 스크립트로 이후 재측정해 비교한다 —
스크립트는 `~/.claude/scripts/measure-pages.mjs`에 있다(저장소에는 커밋하지 않는다,
`c4c183f` 컨벤션 참고). base URL 을 인자로 받으므로 `node ~/.claude/scripts/measure-pages.mjs <base URL>` 로 실행한다.

다만 이 표 자체만으로는 전후 비교의 근거가 약하다 — 6개 행 중 3개(`/companies`·
`/categories`·`/categories/정수기`)는 **2차 중앙값이 1차보다 오히려 높다**(예:
`/companies` 1215ms → 2265ms). 캐시가 없는 상태에서의 노이즈이므로, 캐싱 적용 후
"2차가 뚜렷이 낮아졌다"고 주장하려면 이 표의 절대값이 아니라 같은 조건에서 여러 번
재측정한 범위와 비교해야 한다.
