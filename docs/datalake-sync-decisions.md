# 데이터레이크 싱크 — 사업팀 결정 항목

작성 2026-08-17 · 근거 문서 `docs/rentre_logic_sync_onepager (1).docx`
대조 대상: 이 저장소(`analytics-dashboard`)의 Supabase `raw_orders` / `raw_contracts` / `tps_pnl`

원페이저의 숫자를 우리 DB로 재현해본 결과 **대부분 일치**했다. 그래서 안 맞는 지점이
의미가 있다. 아래는 그 지점들과, 정해야 할 것들이다.

---

## 0. 먼저 — 재현 결과

| 문서 | 우리 DB | 판정 |
|---|---|---|
| 3~5월 공헌이익 15.96억 | 15.96억 | 일치 |
| 3~5월 순주문 17,477건 | 17,256건 (−221) | **−1.3%** |
| 기준값 91,320원/건 | 92,495원/건 (+1,175) | **+1.3%** |
| 6월 순주문 6,284건 / 5.94억 | 6,203건 / 5.92억 | −81건 |
| 적자 거래 0.6% | 0.57% (201/35,103) | 일치 |
| 카테고리 5그룹 비중·건당 cm | 전부 ±0.6%p 이내 | 일치 |

공헌이익은 같은데 **건수만 다르다**. 분모만 어긋나므로 기준값이 1.3% 밀리고,
NSM 환산값과 연말 프로젝션이 같은 비율로 밀린다.

재현 방법: `raw_contracts`를 `contract_date` 기준으로 집계, `contribution_margin` 합.

## D1. GMV 산식 — 지금 두 시스템이 다른 답을 낸다 🔴 즉시

**상태:** 문서는 `GMV = fn_calc_gmv 완전 이식`. 현재 대시보드가 쓰는 Redash 4441은
**단순곱**(월렌탈료 × 기간 × 수량)이라 요금면제·프로모션·정액할인이 빠져 있다.

**실측 격차** (2026년, 월별 통합쿼리 vs 현행 `raw_contracts`):

```
1월 −2.0%   2월 −2.5%   3월 −2.8%   4월 −2.8%
5월 −2.9%   6월 −3.5%   7월 −3.9%   8월 −5.4%
8개월 합계  −3.16%
```

격차가 **최근으로 갈수록 커진다** — 요금면제·프로모션이 늘고 있다는 뜻이고,
현행 단순곱이 최근 데이터를 갈수록 크게 과대계상하고 있다.

**정할 것**
- 회의·보고에서 인용하는 GMV가 어느 산식인지 명시한다.
- 대시보드를 `fn_calc_gmv` 기준으로 언제 넘길지 (= 4678 마이그레이션 일정).

**결정하면** 대시보드 GMV가 약 3% 내려간다. 파트너사별 건당 평균 거래액 순위도 바뀔 수
있다(요금면제를 많이 거는 렌탈사가 더 크게 내려가므로). 관련자 사전 공유 필요.

**참고** 통합 쿼리는 준비됨: `docs/redash-4678-unified-query.sql`

## D2. "순주문"의 정본 상태셋 🔴 즉시

**상태:** 문서는 `순주문 = 설치완료(prop_complete_ts)`이고 `⚠ 확정−취소와 다름`까지
경고했지만, **어떤 `PROP_STAT` 집합이 설치완료인지는 문서에 없다.**

우리 쪽 세 쿼리가 전부 다르다:

| 쿼리 | 계약완료로 보는 상태 |
|---|---|
| Redash 4445 (현행 `raw_contracts`) | `COMPLETE, REQFAIL_H, K, M, N, O` |
| Redash 4678 (통합, `구분` 컬럼) | `COMPLETE, PAYB_WAIT` |
| 데이터레이크 `fact_install` | **미확인** |

4445가 `REQFAIL_*`를 포함하므로 우리 `raw_contracts`에 취소성 건이 섞여 있을 수 있다.
221건 차이의 정체가 여기일 가능성이 높다.

**정할 것**
- `fact_install`의 정본 상태셋 목록을 확보해 우리 쪽과 맞춘다.

**결정하면** 기준값이 확정되고 NSM 전체가 정렬된다. 이게 안 맞으면 아래 D3~D5를
논의해도 숫자가 계속 어긋난다. **선행 항목.**

**확인 방법** 4678을 상태별로 분해하면 221건이 어느 상태인지 특정 가능
(`구분` 대신 주석 처리된 `p.PROP_STAT AS 상세상태`를 켠다).

## D3. 카테고리 체계(M3) — 대시보드 축과 경계가 다르다 🟠

**상태:** 문서 6그룹과 대시보드 5그룹이 서로를 가로지른다.

```
문서      : 대형가전(에어컨·TV·세탁기·냉장고 등 11종)  |  기타(매트리스·안마의자·노트북·청소기 등)
대시보드  : 성장성 카테고리(TV·세탁기·에어컨·냉장고·청소기·안마의자·매트리스·타이어)  |  그외
```

대시보드의 "성장성 카테고리"가 문서의 **대형가전과 기타를 쪼개서 다시 묶는다.**
같은 회의에서 두 축을 섞으면 숫자가 맞지 않는다.

문서도 이걸 M3 핵심 논점으로 적어뒀다 — *"기타(6)에 성격이 다른 카테고리가 섞여 있음
(안마의자·매트리스 = 고단가 vs 소형가전 = 저단가)"*. 실측으로도 기타 건당 10.5만은
대형가전(12.8만)에 가깝고 공청·비데(6.3만)와는 성격이 다르다.

**정할 것**
- 기타(6)를 쪼갤 기준.
- 쪼갠 결과를 대시보드의 "성장성 / 크로스셀 / 그외" 축과 정합시킬지, 아니면 대시보드를
  문서 축으로 갈아탈지.

**결정하면** 데이터레이크는 `dim_prod_category` 1곳 교체로 전 이력 소급되지만,
**대시보드는 별도 수정이 필요하다** (`app/page.tsx`의 `CAT_TABLE_ROWS` /
`LARGE_CATEGORY_GROUPS`). 자동 소급되지 않는다.

## D4. 갱신 주기 — 구조적 불일치 🟠

**상태:** 문서는 `as_of: 자라는 값(원장·정산·귀속)은 매일 전 이력 재계산`.
대시보드 크론은 **2일 창만** 돈다 (`app/api/sync/cron/route.ts`).

**실측:** 정산은 나중에 확정되므로 **하루 만에 14%의 행에서 매출이 바뀐다.**
(어제 20:00 스냅샷 `tps_pnl` vs 당일 실행 비교, 163건 중 공통 행 기준)

즉 대시보드는 과거 정산 확정을 영구히 따라잡지 못하고, 데이터레이크와 시간이 갈수록
벌어진다. 부수 문제로 `raw_orders`에 삭제된 항목(`PROP_ITEM.DEL_YN=1`) **유령행 124건**이
남아 있다 — upsert만 하고 삭제를 반영하지 않는 구조.

```
유령행 분포  1월 0 · 2월 0 · 3월 1 · 4월 0 · 5월 2 · 6월 35 · 7월 62 · 8월 19
```

**정할 것 (택1)**
- (A) 대시보드가 데이터레이크 `stats_*`를 읽는다 → 정의 불일치가 원천적으로 사라진다.
- (B) 대시보드 자체 동기화를 전 이력 재계산으로 바꾼다 → 독립성은 유지되나 중복 유지비.

**추천:** (A). 문서의 "단일 지점 원칙"과 같은 방향이고, D1·D2·D3가 전부 자동 해소된다.
다만 데이터레이크 조회 권한·지연·비용을 확인해야 한다.

## D5. 취소 사유 귀책 분류 — 우리 쪽에 원천이 없다 🟡

**상태:** 문서는 결정 항목이 *"전부 데이터 준비 완료, 규칙만 꽂으면 됨"*이라고 하지만,
취소 사유는 **이 저장소에 원천이 없다.**

- `raw_orders` / `raw_contracts` 26컬럼에 취소 사유 없음
- 4678에도 `취소사유코드`(`p.CANCEL_RSN_TYPE`)가 **주석 처리** 상태
- 문서가 요구하는 5월 스파이크 5,002건 규명은 `fact_order_cancel`(사유 10종) 필요

**정할 것**
- 5월 스파이크 규명이 사업팀 소관인지.
- `fact_order_cancel` 접근 권한이 있는지. 없으면 이 항목은 다음 회의로 미룬다.

**우리 쪽에서 할 수 있는 것** 4678의 주석 3줄(`상세상태`·`취소사유코드`·`취소일`)을 켜면
취소 사유 코드까지 끌어올 수 있다. 사유 → 귀책(고객/파트너/신용) 매핑 규칙만 받으면
대시보드에서도 집계 가능.

## D6. 문서 자체의 결정 항목 (사업팀 소관)

원페이저 Ⅳ "NSM·파트너·정산" 블록에 적힌 것들. 위 D1~D5와 별개로 그대로 남아 있다.

| 항목 | 현 상태 | 비고 |
|---|---|---|
| NSM Actual 데일리 목표 정책 | 잠정 = 월초 90일 평균 | + 월 목표 입력 체계(달성률 지표화) |
| 렌탈사 티어 기준 승인 (M2) | 90일 이동 합성 초안 | |
| 상담 응답 SLA 기준선 | 미정 | 응답 시간 전수 보유 |
| 기타 BM3 장려금 정책 | 점검 필요 | **기타 BM3 64.6%가 적자(구조적)** |
| 가입 소스 통합 분류 우선순위 | 미정 | 마케팅팀 공동 |

`NSM Actual` 데일리 목표는 반영 지점 1곳(`nsm_daily.sql` ref CTE)이고 결정 즉시 전 이력
소급된다고 문서에 명시돼 있다.
