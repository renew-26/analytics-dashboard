prop_item_usid가 raw_orders와 raw_contracts 양쪽에 있으므로 진짜 코호트 추적이 가능합니다. 지금은 이 키를 operation-efficiency에서 두 표를 합치는 데만 쓰고 있습니다.

⑤ 11개월 동안 4.2일 → 6.9일로 64% 늘었습니다. 전환율(최종 94% 안팎)은 거의 그대로인데 도달 속도만 느려지고 있습니다. 비율 지표만 보면 절대 안 보이는 변화이고, 현금 회수 시점이 그만큼 밀린다는 뜻이라 재무에 직접 영향입니다.
구현 노트 새 테이블 · 새 동기화 없이 성립합니다

필요한 건 prop_item_usid 조인 하나입니다. raw_orders와 raw_contracts 양쪽에 이미 있고, operation-efficiency가 같은 방식으로 두 표를 병합하고 있으니 검증된 패턴을 그대로 재사용하면 됩니다.

-- 미결 주문 = 주문은 있는데 계약이 없는 건 SELECT o.prop_item_usid, o.order_confirmed_at, o.rental_company, o.category, o.model_name, o.monthly_fee, o.total_rental_fee, CURRENT_DATE - o.order_confirmed_at::date AS age_days FROM raw_orders o LEFT JOIN raw_contracts c ON c.prop_item_usid = o.prop_item_usid WHERE c.prop_item_usid IS NULL AND o.order_confirmed_at >= CURRENT_DATE - INTERVAL '60 days' ORDER BY age_days DESC; -- 코호트 곡선 = 주문월별, 경과일별 누적 계약률 SELECT to_char(o.order_confirmed_at, 'YYYY-MM') AS cohort, c.contract_date::date - o.order_confirmed_at::date AS days_to_contract FROM raw_orders o JOIN raw_contracts c ON c.prop_item_usid = o.prop_item_usid;

⚠️ 확인이 필요한 전제 하나 — prop_item_usid가 두 표에서 1:1로 대응하는지입니다. 같은 주문이 분할 계약되거나 재계약으로 중복되면 조인이 부풀 수 있습니다. operation-efficiency는 byId.set()으로 덮어쓰기 처리하는데, 그게 의도된 것인지 확인하고 시작하는 게 좋겠습니다.
