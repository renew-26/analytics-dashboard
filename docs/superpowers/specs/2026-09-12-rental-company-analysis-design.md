# 렌탈사 분석 화면 개편 Design

작성 2026-09-12. 카테고리 개편(`2026-09-12-category-analysis-redesign-design.md`)과 짝을 이룬다.

## 핵심 목적

렌탈사별 단순 실적 조회가 아니라, **어떤 렌탈사의 성과가 평소와 다르게 움직이고 있는지**를
빠르게 발견하고, 그 원인을 카테고리 → 브랜드 → 상품/모델 순으로 내려가며 확인한다.

화면의 질문은 "누가 잘했는가"가 아니라 **"어디를 먼저 확인해야 하는가"** 다.

## 카테고리 분석과의 관계

```
카테고리 분석 :  카테고리 → 브랜드 → 렌탈사 → 상품/모델
렌탈사  분석 :  렌탈사 → 카테고리 → 브랜드 → 상품/모델
```

**드릴다운 순서 자체가 질문이다.** 두 화면을 합치면 순서가 하나로 고정되고 나머지
질문은 못 묻게 된다 — 그래서 트리를 둘로 유지한다. 대신 **잎은 공유한다**(아래 "합류점").

렌탈사 분석에서는 **카테고리가 1차 분석축**이다.

## 확정 사항

### 용어 — 단계당 이름 하나

```
견적신청          주문확정              계약완료
quote_date   order_confirmed_at    contract_date
```

**계약완료 = 설치완료 = 설치인증이다(사용자 확정, 2026-09-12).** `raw_prop_items`에 설치일
컬럼은 없고 필요하지도 않다 — `contract_date`가 원천에서 "계약완료일 (지원금 지급일)"이고,
지원금은 설치가 확인돼야 나간다.

화면에서 **"설치완료"·"설치인증"을 쓰지 않는다.** 꼭 필요하면 계약완료 옆에 작은 글씨로
`(설치 확인 시점)`을 한 번만 붙인다. `lib/date-basis.ts`의 `BASIS_LABEL`이 이 이름의
단일 소스다.

이 결정의 귀결로 원 스펙 ⑤ 전환·리드타임의 7줄이 4줄로 줄어든다:

| 원 스펙 | 확정 |
|---|---|
| 주문확정 건수 | 주문확정 건수 |
| 계약완료 건수 / 설치완료 건수 | 계약완료 건수 (하나) |
| 계약완료율 / 설치완료율 | 계약완료율 (하나) |
| 주문→계약 소요일 / 계약→설치 소요일 | 주문→계약 평균 소요일 (하나) |

같은 숫자를 다른 이름으로 두 번 세우면 보는 사람이 "왜 값이 같지?"에서 멈춘다.

### 티어 — 현행 유지, DW 연동하지 않는다

`lib/tiers.ts` 그대로 쓴다 (직전 90일 계약완료 ≥1,500 → T1, ≥100 → T2, 나머지 T3).

DW `rentre_dw_mart.dim_rental_company`에 정본 산식(`install_90d² ÷ consult_90d`)과
상담량이 실제로 있다. 그런데 붙이지 않는다 — **두 방식의 차이가 46개사 중 2개사뿐**이기
때문이다 (dt=2026-09-11 조회):

| 렌탈사 | 계약완료90d | 상담90d | 전환효율 | 상담 반영 | 설치량 단독 |
|---|---:|---:|---:|:--:|:--:|
| BS렌탈 | 110 | 1,793 | 6.1% | T3 | **T2** |
| KT스카이라이프 | 78 | 401 | 19.5% | **T2** | T3 |

**T1 4사(코웨이·LG전자·쿠쿠·SK인텔릭스)는 두 방식이 완전히 동일하다.** 화면에서 가장
중요한 구간이 안 바뀌는데, 컨테이너 AWS 자격증명과 렌탈사 명칭 매핑(DW `SK매직` =
앱 `SK인텔릭스`)을 짊어질 값어치가 없다.

**단 `lib/tiers.ts`의 서술은 고친다.** 주석이 "정본 산식은 상담량을 쓴다"고 적어둔 채
안 쓰고 있어 읽는 사람을 헷갈리게 한다. T2 설명의 "효율 확인"도 상담량 없이는 성립하지
않으므로 실제 판정에 맞는 말로 바꾼다.

티어의 뜻:

| | 성격 | 보는 법 |
|---|---|---|
| T1 | 핵심 | 규모가 크므로 작은 변화도 중요 |
| T2 | 주력 | 중간 규모 구간 |
| T3 | 롱테일 | 개별 모니터링보다 이상 발생 시 확인 |

### COMPANY_MAP을 건드리지 않는다

사이드바 하위는 **기존 `group`**(가전&상조 / 정수기 / 통신)을 그대로 쓴다.
`Sidebar.tsx`의 `NAV_SECTIONS`가 이미 이 묶음을 계산하고 있고, `/group/[group]` 라우트도
이미 있다 — 새로 만들 게 없다.

(더블체크파트너스 / 종합렌탈사 / 인터넷 3분할 개명은 보류. 별건으로 다룬다.)

### 점유율의 분모

**`COMPANY_MAP`에 있는 렌탈사 합계.** 현행 동작 그대로다 — `buildCompanyCards`가
`CARD_DEFS`만 순회하고 매칭 안 되는 행은 `if (!def) continue`로 버린다.

취급하지 않는 렌탈사를 분모에 넣으면 점유율이 우리가 못 건드리는 숫자에 희석된다.

⚠️ 이 전제는 `COMPANY_MAP`이 실제 취급 렌탈사를 다 담고 있을 때만 성립한다.
"열린 항목" 참고.

### 계약완료율 — 코호트 기준

`lib/conversion.ts`의 `conversionStats()`를 쓴다. **분모 = 기간 내 주문확정, 분자 =
그중 계약완료** — 코호트 기준이다.

기간 기준(이번 달 계약완료 ÷ 이번 달 주문확정)으로 재면 분자·분모가 다른 코호트라
리드타임만큼 어긋나고, 주문이 늘어난 달은 전환율이 인위적으로 떨어져 **잘하고 있는데
나빠 보인다.** 원 스펙의 "후행 반영 가능성" 판단이 정확히 이 문제이고, 기간 기준으로는
그 판단 자체가 불가능하다.

**절단 보정은 하지 않는다**(카테고리 계획 Global Constraints와 동일). 전환이 익는 데
30일이 걸린다 — 정수기 실측 7일 60.5% · 14일 75.5% · 30일 84.0%.

**대신 `집계 중` 라벨을 붙인다.** 값은 그대로 두고, 아직 안 익은 구간에 표기만 한다.
보정이 아니라 라벨이므로 위 제약과 어긋나지 않는다. `DESIGN.md`의 *"진행 중인 마지막
데이터 점은 속을 비운 원으로 표시한다"*를 숫자에 적용한 것이다.

### 색 규칙

`DESIGN.md` 그대로. 이 화면에서 특히 갈리는 지점:

| 지표 | 색 |
|---|---|
| 계약완료 · 거래액 · 매출 증감 | **방향색** (`--color-up` / `--color-down`) |
| 주문→계약 소요일 | **심각도색** + 텍스트 라벨 — 오르면 나쁜 지표다 |
| 계약완료율 | **심각도색** + 텍스트 라벨 — 떨어지면 나쁜 지표다 |

리드타임에 방향색을 쓰면 빨강이 "상승"과 "위험"을 동시에 뜻하게 되어 거짓말이 된다.

### 정렬은 비율이 아니라 건수

우선순위·기여 분해 모두 **절대 변화량(건수)** 으로 정렬한다.

```
코웨이  -8.2%  →  -107건   ← 위
넥센    -50%   →   -14건   ← 아래
```

원 스펙의 "규모가 큰 렌탈사의 이상 변화"가 이것으로 자동 충족된다 — 별도 티어 가중치가
필요 없다. 비율로 정렬하면 몇 건만 움직여도 비율이 튀는 T3 롱테일이 상단을 차지한다.

`lib/decompose.ts`의 `diffMap()`이 이미 `Math.abs` 기준으로 정렬한다.

## 화면 1 — 렌탈사 홈 (`/companies`)

```
┌─ ① 전체 현황 ────────────────────────────────────┐
│  규모 (24px)    계약완료   거래액   매출            │
│  효율·속도(20px) 건당 공헌이익  계약완료율  소요일   │
│  각 값에 전월 / 평소 페이스 대비 병기               │
└─────────────────────────────────────────────────┘

┌─ ② 지금 봐야 하는 곳 ─────────────────────────────┐
│  [카드] [카드] [카드]                              │
│  [카드] [카드] [카드]      영향량 상위 6곳          │
└─────────────────────────────────────────────────┘

┌─ ③ 렌탈사별 성과 ────────────────────────────────┐
│  [전체][T1][T2][기타]     ← 티어 필터는 여기만     │
│  표 (전 렌탈사)                                    │
└─────────────────────────────────────────────────┘
```

### ①은 주인공이 아니다

6개 KPI를 같은 크기 타일로 늘어놓으면 상단을 다 먹고 ②가 스크롤 아래로 밀린다.
화면의 목적("어디를 먼저 확인")과 배치가 반대가 된다.

그래서 **성격으로 나눠 크기를 다르게** 한다 — 규모 3개는 24px, 효율·속도 3개는 20px.
"얼마나"와 "어떻게"는 다른 질문이고, 같은 크기로 늘어놓으면 비교가 안 된다.

### ②는 트리거별로 섹션을 나누지 않는다

원 스펙의 `이상 / 급증 / 급감 / 평소 대비 변화`를 각각 줄로 세우면 **같은 렌탈사가 여러
줄에 중복**된다 — 계약완료 급감과 리드타임 급증은 대개 같은 원인의 두 얼굴이다. 그러면
"몇 군데를 봐야 하는지"를 셀 수 없다.

**렌탈사 한 곳당 카드 한 장**으로 하고, 걸린 트리거를 배지로 붙인다.

```
[T1] 코웨이                          /company/코웨이

계약완료  1,204건   ▼ 8.2%   평소 대비 76%
[급감]  [리드타임 주의]

거래액 12.4억 · 매출 3.2억 · 건당 공헌이익 11.5만
```

경로(`/company/코웨이`)를 `--font-mono`로 병기하는 것은 `DESIGN.md`의 "목적지를 숨기지
않는다".

**빈 상태**: 아무 데도 안 걸리면 `지금 특별히 볼 곳 없음 — N개사 모두 평소 범위`.
빈 영역을 남기지 않는다.

**티어 필터는 ③에만 건다.** ②는 "지금 봐야 할 곳"인데 필터로 가리면 볼 곳을 숨기는
셈이 된다.

**②는 ③의 발췌다** — 같은 데이터, 같은 판정. 카드 클릭과 표 행 클릭이 같은 곳으로 간다.

### 트리거 6개와 현재 상태

| 트리거 | 상태 |
|---|---|
| 평소 페이스 대비 급증/급감 | ✅ `lib/status.ts` `judgeState(curr, pace)` |
| 전월 대비 큰 변화 | ✅ `curr` / `prev` |
| 규모 큰 렌탈사의 이상 변화 | ✅ 건수 정렬로 자동 |
| 공헌이익 급변 | ⚠️ 전월 cpu 미계산 — `pRows` 마진 합 |
| 계약완료율 급변 | ❌ `order_confirmed_at` 미수집 |
| 리드타임 급변 | ❌ 동상 |

판정 축은 **하나로 유지한다** — 새 트리거도 `judgeState`를 쓴다. 화면에 판정 기준이
둘이면 읽는 사람이 뭘 믿을지 몰라진다.

## 화면 2 — 렌탈사 상세 (`/company/[company]`)

```
SK인텔릭스                                    [T1]

┌─ ① 전체 성과 ────────────────────────────────────┐
│  계약완료 97건 ▼1건   거래액 2.3억   건당 공헌이익 11.5만 │
└─────────────────────────────────────────────────┘

┌─ ② 카테고리별 성과 ★ ────────────────────────────┐
│              계약완료  증감  점유율  거래액  매출  공헌이익 │
│  정수기         96건   -1   99.0%  2.3억  …          │
│  공청기·비데      1건    0    1.0%  0.0억  …          │
│  대형가전         0건    0      —      —             │
│  타이어           0건    0      —      —             │
│  기타             0건    0      —      —             │
│  인터넷           0건    0      —      —             │
└─────────────────────────────────────────────────┘

③ 브랜드별 성과 · ④ 상품/모델별 성과 · ⑤ 전환·리드타임
```

### 카테고리 축은 `catGroupOf()`

`lib/biz-category.ts`의 6그룹(정수기 · 공청기·비데 · 대형가전 · 타이어 · 기타 · 인터넷)을
그대로 쓴다. 원 스펙에 적힌 6개와 정확히 일치한다.

이 함수를 쓰면 **카테고리 트리와 자동으로 싱크된다.** 렌탈사 쪽에 별도 매핑을 만들면
두 화면이 갈라지고, M3 확정 때 두 곳을 고쳐야 한다.

### 0건 카테고리를 숨기지 않는다

"이 렌탈사는 정수기만 판다"가 한눈에 보이고, 크로스셀 여지가 어디인지도 같이 보인다.
**안 파는 것이 정보다.** 다만 회색으로 눕혀 시선은 뺏지 않는다.

(카테고리 계획의 "조건부 노출을 넣지 않는다"와 같은 원칙이다.)

### 판정은 자기 과거 대비

카테고리 행마다 `judgeState(curr, pace)`. `pace`는 **그 렌탈사 × 그 카테고리**의 최근
3개월 같은 기간 평균. `DESIGN.md`의 *"판정 기준은 자기 과거 대비로, 목표치 입력 없이
성립하게"* 그대로다.

### 합류점 — 드릴다운 뒷부분은 이미 있다

```
/company/SK인텔릭스
   └ "정수기" 행 클릭
      → /categories/정수기/SK인텔릭스              (기존, 652줄)
         └ 상품 클릭
            → /categories/정수기/SK인텔릭스/[product]  (기존)
```

**새 라우트를 만들지 않는다.** 카테고리 트리와 렌탈사 트리가 이 지점에서 합류하므로
잎(상품·브랜드 표)을 두 벌 만들 필요가 없다.

### 파일 분리는 필요한 만큼만

`app/company/[company]/page.tsx`가 2,785줄이고 집계 함수 7개 + fetch 함수 6개가 전부
이 안에 있다. ①②가 실제로 쓰는 것까지만 뽑는다.

```
app/company/[company]/page.tsx        fetch + 조립
app/components/company-detail/
  ├ Overview.tsx                      ① 전체 성과
  └ CategoryBreakdown.tsx             ② 카테고리별 성과 ★
```

**나머지 2,000여 줄은 그대로 둔다.** 지금 안 쓰는 코드를 옮기다 깨뜨릴 위험만 크다.

## 데이터 계층

### fetch가 두 번 필요하다

`fetchRows`는 `basis`로 고른 날짜 컬럼이 **not null인 행만** 가져온다:

```ts
.not(dateColumn, "is", null).gte(dateColumn, start)
```

`/companies`는 `basis: "contract"`라 계약완료된 행만 온다. **주문확정은 됐지만 아직 계약
전인 행이 안 들어와서 계약완료율의 분모가 통째로 빠진다.**

```
fetch A  basis: "contract"   ← 기존 (+ order_confirmed_at 컬럼 추가)
fetch B  basis: "order"      ← 신규, 계약완료율 분모 전용
```

A에 컬럼 하나만 더하면 **리드타임과 전월 cpu는 해결된다.** B는 계약완료율 전용이므로,
부담되면 계약완료율만 뒤로 미룰 수 있다.

### `buildCompanyCards`에 더할 필드

```ts
cpuPrev       전월 건당 공헌이익      pRows 마진 합
leadDays      주문→계약 평균 소요일    fetch A
leadDaysPrev  전월 동일
convRate      계약완료율 (코호트)      fetch B · conversionStats()
convRatePrev  전월 동일
convMature    코호트 성숙 여부         `집계 중` 라벨 판정
```

### 소요일은 평균으로 간다

원 스펙이 "평균"이라 적었으므로 평균으로 한다. 다만 평균은 늦게 계약된 롱테일 몇 건에
크게 끌린다 — 실제 분포를 보고 중앙값이 나으면 그때 바꾼다. "열린 항목" 참고.

## IA 이관

`Sidebar.tsx`의 규칙: *"마이그레이션 완료분은 1차 내비로 올린다 — 나머지는 아래
'기타 분석'에 남는다."*

### 지금 레거시에 묻혀 있는 것

```
기타 분석 ▾
├ [렌탈사별 매출 추이]
│   가전&상조 ▾ → /group/가전&상조 (871줄) + 개별 렌탈사 /company/…
│   정수기   ▾ → /group/정수기
│   통신     ▾ → /group/통신
├ [상품 전략]     운영효율뷰 · 카테고리 트렌드 · 카테고리 상세 · 브랜드 분석
├ [렌탈사 분석]   렌탈사 비교 /compare (231줄) · 전환율 분석 /conversion (153줄)
└ [시장 정보]     타사 비교 · 상품 관리 · 상품 지원금 조회 · 조사 상품 선정 ×2
```

**개편 대상인 `/company/[label]`이 3단 안쪽에 있다** — `기타 분석 ▾` → `렌탈사별 매출
추이` → `가전&상조 ▾`. 세 번 펼쳐야 도달한다.

### 목표 형태

```
홈
카테고리        /categories
  ├ 정수기 · 공청기·비데 · 대형가전 · 타이어 · 기타 · 인터넷
렌탈사          /companies
  ├ 가전&상조     /group/가전&상조     ← 이미 있음, 위치만 이동
  ├ 정수기        /group/정수기
  └ 통신          /group/통신
예외승인 분석
```

### 순서

```
A 슬라이스 완료 (①전체현황 → ②우선순위 → ④카테고리별 성과 ★)
  ↓
승격  /group/[group] ×3 → 렌탈사 하위
      /company/[label]  → 레거시에서 빼기
  ↓
나머지 완료 (③브랜드 · ④상품/모델 · ⑤전환·리드타임 · 티어필터)
  ↓
흡수 확인 후 제거  /conversion · /compare
  ↓
"렌탈사별 매출 추이" 섹션 소멸
```

승격을 A 직후에 두는 이유: `/group/[group]`은 이미 완성된 화면이라 개편을 기다릴 필요가
없고, 올려두면 개편 중인 `/company/[label]`로 가는 길이 세 번 클릭에서 두 번으로 줄어
**작업하면서 직접 써볼 수 있다.**

### 흡수 대상 둘

| 레거시 | 겹치는 곳 | 처리 |
|---|---|---|
| `/conversion` 전환율 분석 (153줄) | 상세 ⑤ 전환·리드타임 | 흡수 후 제거 |
| `/compare` 렌탈사 비교 (231줄) | 홈 ③ 렌탈사별 성과 표 | 흡수 후 제거 |

같은 숫자를 두 화면이 각자 계산하면 언젠가 갈라지고, 갈라지면 어느 쪽이 맞는지 아무도
모르게 된다. **다만 실제로 대체된 것을 확인한 뒤에 지운다** — 먼저 지우면 그 사이에
쓸 화면이 없어진다.

## 구현 순서 — 세로로 한 줄 먼저 관통

```
① 전체 현황 → ② 우선순위 → 클릭 → ④ 상세의 카테고리별 성과 ★
```

여기까지 먼저 동작시키고 브랜드·모델·리드타임·티어필터를 뒤에 붙인다.

스펙이 상세해서 "무엇을 만들지"는 이미 정해졌고, 남은 미지수는 **"이 흐름이 실제로
원인을 짚어주는가"** 다. 그건 세로로 한 줄 뚫어봐야만 알 수 있다. 아니라고 판명돼도
버리는 게 가장 적다.

## 열린 항목

### 삼성전자가 `COMPANY_MAP`에 없다

DW `dim_rental_company`(dt=2026-09-11)에 **삼성전자 90일 설치 130건**이 찍혀 있는데
`COMPANY_MAP`에 항목이 없다. BS렌탈(110)보다 큰 규모다. 웅진 13건도 마찬가지다.

`COMPANY_MAP`의 교원웰스 주석이 같은 일을 기록해 뒀다 — *"2026-03 계약완료가 월 5건대에서
80건대로 뛴 뒤 지도에 반영되지 않고 있던 곳."*

**누락이라면 현재 화면의 합계·점유율이 이미 틀린 것이다.** 다만 DW 기준이라
`raw_prop_items`에 실제 행이 있는지 확인이 필요하다:

```sql
select rental_company, count(*) as cnt, max(contract_date) as last_dt
from raw_prop_items
where contract_date >= current_date - interval '90 days'
group by rental_company
order by cnt desc;
```

미실행. 이 개편과 별건으로 처리한다.
