# 대시보드 로딩 개선 — 마이그레이션 완주 후 캐싱

작성 2026-09-11. 선행 문서 `docs/performance-plan.md`(1단계 병렬화 적용분)를 잇는다.
그 문서가 "받는 양 자체를 줄이거나 같은 일을 다시 안 하기"로 남긴 2·3단계를,
**진행 중인 4678 통합 마이그레이션과 묶어** 순서대로 처리한다.

## 왜 이 문서가 필요한가

"item_prop 마이그레이션 후 페이지가 느리다"는 관찰로 시작했는데, 실측하니 전제가
달랐다. **마이그레이션이 끝나지 않았고, 안 끝난 것이 느림의 원인과 얽혀 있다.**
그래서 성능만 손대면 안 되고 순서가 설계의 본체가 된다.

### 쿼리 비용

워밍업 후 중앙값 3회:

| 쿼리 | 시간 | 행 |
|---|---:|---:|
| `raw_prop_items` 전체 `count(*)` (콜드) | 2,900ms | 131,699 |
| exception-approval `fetchAllRows` (15컬럼) | 476ms | 13,286 |
| **같은 행수, 1컬럼만** | **65ms** | 13,286 |
| `category` 필터 | 194ms | 13,286 |
| PK 1건 | 85ms | 1 |

읽을 것 둘:

1. **인덱스는 병목이 아니다.** 필터·정렬·PK가 모두 100~200ms대다.
   `performance-plan.md` 가 "인덱스 상태 미확인"으로 남긴 항목은 워밍업 후 문제없다.
2. **페이로드가 병목이다.** 같은 13,286행이 컬럼 15개면 476ms, 1개면 65ms — **7배**.
   집계에 쓸 값 수십 개를 얻으려고 행×컬럼을 통째로 옮기는 비용이다.

`PostgREST` 집계 함수는 여전히 꺼져 있다 (`PGRST123`).

| 항목 | 결정 | 근거 |

## 순서와 게이트

각 단계는 **숫자로 확인**한 뒤 다음으로 넘어간다.

```
① 배포 최신화
   게이트: 다음 05:00 KST 이후 raw_prop_items.synced_at 이 20:00 UTC 대로 찍힌다

② PHASE 2 뷰 전환 — ①과 같은 날
   게이트: migrations/2026-09-04_phase2_views.sql 하단 확인 쿼리 2개가 모두 true

③ 재측정
   게이트: 프로덕션 빌드 · 페이지별 5회 중앙값 기록

④ 캐싱 (A안)
   게이트: 동일 페이지 1차/2차 요청 분리 측정 — 2차가 즉시인지
```

### ①②를 묶어야 하는 이유

순서에 함정이 있다.

- **배포만 먼저 하면** — 새 크론은 `order`/`contract` 를 부르지 않는다. 구 테이블이
  그날부터 얼고, 30개 사용처가 조용히 낡은 숫자를 보여준다.
- **PHASE 2 만 먼저 하면** — 구 크론(배포된 낡은 코드)이 매일 `raw_orders` 에 upsert 를
  시도하는데 그것이 뷰가 되어 쓰기가 실패한다. 매일 밤 동기화 에러.

배포 → 같은 날 PHASE 2 순서면 구 테이블 동결 창이 몇 시간으로 줄고, 그 사이 페이지는
배포 시점 데이터를 보여준다. 반대 순서는 크론 실패를 감수해야 하므로 이쪽을 택한다.

## ④ 캐싱 상세 (A안)

`force-dynamic` 을 떼고, 크론 끝에 무효화를 넣는다.

```ts
// app/api/sync/cron/route.ts — 동기화 완료 후
revalidatePath("/", "layout");
```

데이터가 하루 한 번 통째로 바뀌므로 페이지별로 골라 깰 이유가 없다.
각 페이지에 안전망 `export const revalidate = 86400` 을 둔다 — **크론이 실패해도
캐시가 영구히 얼지 않게** 하는 장치다.

### 2트랙이어야 한다 — 계획 작성 중 발견 (2026-09-11 정정)

이 절의 초안은 "`force-dynamic` 만 떼면 된다 · 조회 계층은 건드리지 않는다"고 적었다.
**틀렸다.** Next.js App Router 에서 `searchParams` 접근은 동적 렌더링을 강제하므로,
그 페이지는 `force-dynamic` 을 떼도 라우트 세그먼트 캐싱이 들지 않는다.

실측: `force-dynamic` 21개 중 **10개가 `searchParams` 를 읽고**, 그중에 가장 무거운
두 개가 들어 있다.

| 페이지 | `searchParams` | 프로덕션 중앙값 | 라우트 캐싱 |
|---|:---:|---:|:---:|
| `/company/[company]` | 읽음 (`tab`·`bm`) | 2.49s · `.from()` 28회 | ❌ |
| `/` | 읽음 (`hide2025`) | 2.32s | ❌ |
| `/companies` | 안 읽음 | 1.75s | ✅ |
| `/categories` | 안 읽음 | 1.6s | ✅ |
| `/categories/정수기` | 안 읽음 | 2.2s | ✅ |

그래서 두 트랙으로 간다:

- **트랙 1 — 라우트 세그먼트 캐싱 (11개 페이지 대상, 실측 결과 7개만 실제로 캐싱됨).**
  `searchParams` 를 읽지 않는 11개 페이지에서 `force-dynamic` 을 떼고
  `revalidate = 86400` 을 둔다. 조회 계층을 건드리지 않는다. 정정(구현 후 실측,
  `.next/prerender-manifest.json`) — `initialRevalidateSeconds: 86400` 이 붙고
  `dynamicRoutes` 가 빈 라우트는 **7개**뿐이다. 나머지 4개(`app/category/[category]`·
  `app/group/[group]`·`app/categories/[category]/[company]`·`.../[product]`)는
  동적 세그먼트인데 `generateStaticParams` 가 없어 Next 가 `revalidate` 를 그냥
  버린다 — 줄 자체는 무동작이다. `generateStaticParams` 를 일부러 안 붙였다 —
  붙이면 렌탈사 약 30곳의 무거운 Supabase 조회를 빌드 시점에 전부 프리렌더해야
  해서, 빌드가 길어지고 깨지기 쉬워진다(`.superpowers/sdd/2026-09-11-dashboard-loading/progress.md`
  concern 3 ruling 참고). 그래서 이 4개는 무동작인 `revalidate` 줄을 **의도적으로
  그대로 둔다** — 나중에 `generateStaticParams` 가 붙으면 바로 살아나고, 지우는
  편이 오히려 처음부터 다시 판단해야 하는 churn 이다.
- **트랙 2 — 조회 캐싱 (무거운 2개).** `/` 와 `/company/[company]` 의 조회 함수를
  `unstable_cache` 로 감싼다. 캐시 키 규칙은 "searchParams 는 다 뺀다"가 아니라
  **"조회 자체가 그 값에 따라 분기하는 것만 넣는다"** 다 — `hide2025` 는 표시용이고
  (`app/page.tsx:421`), `bm` 은 831행 JS 필터라 둘 다 정당하게 빠진다. 반면
  **`view`(`tab`)는 뺄 수 없다.** 렌탈사 상세의 `fetchGrowthRows`
  (`app/company/[company]/page.tsx:761` 부근)는 view 에 따라 SQL이 읽는 테이블
  자체가 갈린다 — `raw_orders`(주문확정) vs `raw_contracts`(계약완료), 날짜 컬럼도
  `order_confirmed_at` vs `contract_date`로 다르다. view 를 키에서 빼면
  `?tab=contract` 로 들어온 요청이 `?tab=order`(기본)가 채워 둔 `raw_orders` 캐시를
  그대로 받아, 주문확정 행을 계약완료 라벨로 보여주는 정합성 오염이 난다. 그래서
  구현은 `fetchGrowthRows` 에만 `view` 를 인자로 받아 캐시 키에 넣고, 나머지 5개
  조회에는 넣지 않는다(그 조회들은 view 에 따라 SQL이 갈리지 않는다).

트랙 2 는 그 두 파일의 조회를 모듈 스코프 함수로 들어내야 한다(`unstable_cache` 가
요구한다). 이는 "조회 계층 통합"이 아니다 — 나머지 14개 파일로 번지게 하지 않는다.

### `cacheComponents` 를 켜지 않는다

`unstable_cache` 는 Next 16 에서 `'use cache'` 지시어로 대체됐다. 그런데 그 지시어는
`cacheComponents: true` 를 요구하고, 켜면 **`dynamic`·`revalidate`·`fetchCache` 를
export 하는 모든 라우트가 에러가 된다.** 21개 페이지를 한꺼번에 Suspense 구조로
재편해야 하는 별개의 대형 마이그레이션이다. 이 작업은 플래그 없이 동작하는
`revalidate` + `unstable_cache` + `revalidatePath` 로 간다. deprecated API 를 쓰는
이유를 코드 주석에 남긴다.

### 지켜야 할 것

- **`force-dynamic` 21개를 일괄로 떼지 않는다.** 붙은 이유가 페이지마다 다를 수 있다.
  `searchParams` 를 읽는 10개는 위 트랙 구분에 따라 그대로 둔다.
- **캐싱은 숫자를 바꾸면 안 된다.** 트랙 2 는 캐시 키를 잘못 잡으면 다른 기간·다른
  회사의 결과를 조용히 재사용한다. 적용 전후로 화면 대표값을 대조하고,
  `?tab=contract` 가 기본과 다른 값을 내는지 확인한다.

### 받아들이는 트레이드오프 — 빌드 시 프로덕션 Supabase 조회 실패

`force-dynamic` 을 떼면 트랙 1의 7개 페이지가 **빌드 시점에 프리렌더**된다 — 즉
`next build` 가 그 페이지들의 데이터 조회를 실행하며 프로덕션 Supabase 를 부른다.
`force-dynamic` 이 걸려 있던 이전에는 모든 조회가 요청 시점에만 일어나 이 경로가
존재하지 않았다.

문제는 두 데이터 헬퍼가 **에러를 조용히 삼킨다**는 점이다 — `lib/fetch-rows.ts:49`
는 `error`(또는 빈 응답)를 만나면 `break` 로 빠져나와 그때까지 모은 행(빌드
시점이면 보통 `[]`)을 그대로 반환하고, `lib/period.ts:57` 은 `catch` 로 `null` 을
반환한다. 둘 다 throw 하지 않는다. 그래서 빌드 도중 Supabase 가 일시적으로
응답하지 않으면(네트워크 블립, rate limit 등) **빌드는 실패하지 않고 성공한다** —
다만 그 페이지들은 0행 집계가 정적으로 구워져 이미지에 박힌다. 배포되면 다음
05:00 KST 크론이 `revalidatePath` 로 무효화할 때까지, 최악의 경우 **거의 24시간**
빈 화면(또는 0/—로 찍히는 집계)이 서빙된다.

**받아들인다** — `lib/fetch-rows.ts`·`lib/period.ts` 의 에러 처리를 바꾸는 것은
런타임 동작 변경이라 이 작업 범위 밖이다(요청 시점 실패 시 빈 배열을 반환하는
현재 동작에 의존하는 다른 호출부가 있을 수 있다). 완화책(빌드 시 헬스체크,
재시도, 또는 throw 로 바꿔 빌드 자체를 실패시키기)은 후속 과제로 남긴다.

효과의 성격 — 정정(구현 후 실측, 2026-09-11): 당초 "동기화 후 **첫 방문자만** 비용을
내고 나머지는 즉시다"라고 적었으나, 이는 **트랙 1의 7개 경량 페이지에만** 참이다.
트랙 2의 무거운 2개(`/`·`/company/[company]`)는 `unstable_cache` 가 항목당 약 2MB
제한을 두는데, 다음 세 조회가 그 한도를 넘어 조용히 저장되지 않는다(Next 는 경고
로그만 남기고 throw 하지 않으므로 정확성은 무해하지만 캐싱 효과가 없다):

| 조회 | 크기 | 행 수 |
|---|---:|---:|
| 홈 · 올해 주문확정(`fetchAllYearOrders`) | 6.71 MB | 68,455 |
| 홈 · 올해 계약완료(`fetchAllYearContracts`) | 4.19 MB | 45,315 |
| 렌탈사 상세 · IA/티어 12개월(`fetchIaAll`) | 3.51 MB | 21,232 |

즉 이 두 페이지는 동기화 후에도 **매 방문자가 전체 비용을 낸다.** 근본 원인은
집계값 수십 개를 얻으려고 행×컬럼을 통째로 옮기는 구조라 — 원시 행을 캐싱하는
접근 자체가 이 데이터 규모에서 틀렸다. 그래서 아래 B안(집계를 Postgres 로 미는 것)은
"필요하면 한다"가 아니라 **필수**다.

## 집계 SQL (B안) — 이제 필수, 범위는 ③ 이후에 정한다

당초 "아픈 곳이 없으면 'B안 불필요'로 닫는다"고 적었으나, 위 실측이 뒤집었다 — 캐싱만으로는
아픈 곳(두 무거운 페이지)이 그대로 남는다. B안을 **건너뛸 수 있는 선택지가 아니라
다음 단계로 확정**한다. 범위(어느 집계를 matview 로 내릴지)는 뷰 전환 후 재측정에서
정한다 — 뷰 전환이 성능 특성을 바꾸므로(뷰는 조회마다 `raw_prop_items` 를
필터링한다) 현재 숫자로 설계하면 헛짚는다. ③ 측정 후 "어느 쿼리가 여전히
아픈지"를 보고 그 집계만 내린다. 위 세 조회(특히 두 6~7MB짜리)가 유력한 1순위
후보다.

하루 한 번 쓰는 데이터라 **matview + 크론 refresh** 가 자연스럽게 맞는다.
가장 무거운 후보는 `performance-plan.md` 가 지목한 포지션 차트용 4만 행이다 —
필요한 값은 "회사 × 카테고리 건수" 수십 개뿐이다.

SQL 은 이 저장소에서 작성해 넘기고, 적용은 사용자가 한다.

## 미결 항목

### 잔여 160건 — PHASE 2 전 판정 필요

`raw_orders` 에만 있고 4678 이 반환하지 않는 행 160건(전체의 **0.23%**, `sales` 합
3,876만원). 렌탈사·카테고리 전반에 걸쳐 있고 `sales` 가 모두 non-null 이며, 구 크론이
2026-05-31 ~ 09-09 에 걸쳐 넣었다. 해당 월을 백필했는데도 들어오지 않았다.

두 쿼리를 대조한 결과 **조인 구조와 `PROP_STAT` 화이트리스트가 완전히 동일**하고,
날짜 조건은 4678 이 오히려 상위집합이다(`CONFIRMED_TS` **또는** `PROP_COMPLETE_TS`).
따라서 남은 설명은 **원본에서 상태가 바뀌어 이제 양쪽 쿼리 모두에서 빠진다** 는 것뿐이다 —
`raw_orders` 의 그 행들은 과거 스냅샷이다.

확인용 SQL (운영 MySQL. 작성 시점에 VPN 미연결로 실행 못 함):

```sql
SELECT p.PROP_STAT, p.DEL_YN AS prop_del, pi.DEL_YN AS item_del, COUNT(*) AS cnt
FROM PROP_ITEM pi
JOIN PROP p ON p.PROP_USID = pi.PROP_USID
WHERE pi.PROP_ITEM_USID IN (4239777,4963527,5410876,5490595,6614436,6684760,6643171,6699838,6711137,7115290)
GROUP BY p.PROP_STAT, p.DEL_YN, pi.DEL_YN
ORDER BY cnt DESC;
```

위 10건은 표본이다. 전체 160건 목록은 언제든 재생성할 수 있다 —
`raw_orders` 의 `prop_item_usid` 집합에서 `raw_prop_items` 의 것을 빼면 된다
(두 테이블 모두 `prop_item_usid` 로 전건 조회 후 차집합). 백필이 더 돌면 수가 줄 수 있으므로
판정 시점에 다시 뽑는 것이 맞다.

`PROP_STAT` 이 화이트리스트(`INS_ARN`·`INS_RSV`·`CON_RVW`·`PAYB_WAIT`·`COMPLETE`·
`REQFAIL_H/I/J/K`) 밖이거나 `DEL_YN=1` 이면 정당한 제외이고 PHASE 2 가 안전하다.
그렇지 않으면 4678 의 결함이므로 PHASE 2 를 보류하고 쿼리를 고친다.

### 이 문서가 다루지 않는, 확인된 사실

- **`rentre.config.json` 에 `type`·`observability` 절이 없다** — 마켓플레이스 새 스키마
  마이그레이션 필요. 배포(①)와 같은 화면을 만지므로 함께 처리하면 편하다.
- **AGENTS.md 3곳이 지워진 `vercel.json` 을 아직 설명한다** — 실제 구조는
  마켓플레이스 컨테이너 + `instrumentation.ts` node-cron + `ENABLE_CRON` 게이트다.
  이 오독을 한 번 밟았으므로 고쳐 둘 값이 있다.

## 하지 않는 것

- **조회 계층 통합** — 16개 인라인 루프를 `lib/fetch-rows.ts` 로 모으는 일.
  트랙 2 가 두 파일의 조회를 함수로 들어내지만 그건 `unstable_cache` 가 모듈 스코프
  함수를 요구해서다. 나머지 14개 파일로 번지게 하지 않는다 — 섞으면 성능 개선의
  효과와 리팩터링의 위험이 한 diff에 들어가 원인 판별이 안 된다.
- **PostgREST 집계 함수 전역 켜기** — 결정 사항 표 참조.
- **Suspense 스트리밍** — A 적용 후 첫 방문자만 남으면 그때 판단한다. A는 "두 번째
  방문자를 빠르게", 스트리밍은 "첫 방문자가 빈 화면을 안 보게" 로 성격이 다르다.
- **레거시 페이지 성능** — 사이드바 `기타 분석` 아래는 측정만 한다.

## 검증

`performance-plan.md` 가 남긴 교훈을 따른다 — **dev 측정은 노이즈가 신호보다 크다**
(같은 코드 두 번 잰 값이 3.5s ↔ 4.7s로 갈렸다). 그래서:

- 프로덕션 빌드로 재고, 페이지별 **5회 중앙값**을 기록한다.
- 캐시 효과는 **1차 요청과 2차 요청을 분리**해 잰다. 합쳐 재면 캐시가 들었는지 알 수 없다.
- 각 게이트의 판정은 숫자로 남긴다. "빨라진 것 같다"로 넘어가지 않는다.
